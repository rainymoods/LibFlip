# Memory Hammering Patterns

The `hammer_pattern_sample.json` outlines representative hammering patterns, which include detailed information such as the hammering sequences generated by the fuzzer, the physical memory layouts used to instantiate these sequences, and the bit-flip events obtained during execution.

---

## 1. Top Data Structure

The root object is organized into the following two sections:

* **`hammering_patterns`** : Contains the generated hammering patterns.
* **`metadata`** : Records the runtime fuzzing configurations.

---

## 2. Field Specifications

#### 2.1 `hammering_patterns` element

- ``id``: Unique UUID assigned to the pattern.
- ``base_period``: Pattern period expressed in slots.
- ``max_period``: Upper bound of the pattern period.
- ``total_activations``: Number of memory activations represented by the pattern. This equals the size of `access_ids`.
- ``num_refresh_intervals``: Number of refresh intervals spanned by the pattern.
- ``is_location_dependent``: Boolean indicating whether the pattern is tied to a particular memory location.
- ``access_ids``: Fully expanded hammering sequence, where each element identifies an aggressor access.
- ``agg_access_patterns``: The aggressor access patterns.
- ``address_mappings``: Physical-address instantiations of the pattern and the corresponding experimental observations.

#### 2.2 `agg_access_patterns` element

- ``aggressors``: Aggressor IDs belonging to the group.
- ``frequency``: Distance, in slots, between successive occurrences of the group.
- ``amplitude``: Number of adjacent repetitions produced at each occurrence.
- ``start_offset``: Position at which the group first appears in the sequence.

#### 2.3 `address_mappings` element

- ``id``: UUID assigned to the mapping.
- ``bank_no``: DRAM bank selected for the experiment.
- ``min_row` / `max_row``: Lower and upper row numbers covered by the mapping.
- ``aggressor_to_addr``: Associates each aggressor ID with its physical DRAM location, specified by bank, row, and column.
- ``bit_flips``: Collection of bit-flip observations produced with this mapping.
- ``reproducibility_score``: Score indicating the reproducibility of the result.
- ``code_jitter``: Execution-level jitter settings used for the hammering experiment.

#### 2.4 `bit_flips` element

- ``addr``: Virtual memory address associated with the observed flip.
- ``page_offset``: Position of the affected location relative to the beginning of its memory page.
- ``bitmask``: Identifies which bits changed. Each `1` in the mask represents a flipped bit.
- ``data``: Value of the data after corruption.
- ``dram_addr``: Physical DRAM location associated with the affected cell.
- ``observed_at``: Time at which the event was recorded.

#### 2.5 `code_jitter` element

- ``fencing_strategy` / `flushing_strategy``: Fence and cache-flush insertion policies used during execution.
- ``num_aggs_for_sync``: Number of aggressors participating in synchronization.
- ``pattern_sync_each_ref``: Indicates whether pattern synchronization is performed at every refresh interval.
- ``total_activations``: Number of activations executed under this configuration.

#### 2.6 `metadata` element

- ``dimm_id``: Identifier of the DIMM involved in the run.
- ``start` / `end``: Timestamps delimiting the beginning and end of the fuzzing session.
- ``num_patterns``: Total number of patterns generated in the session.
- ``memory_config``: Description of the tested memory configuration.
